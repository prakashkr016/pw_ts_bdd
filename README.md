# pw_ts_bdd — Hybrid BDD Test Automation Framework

An end-to-end test automation framework for an e-commerce website, built with **Playwright**, **TypeScript** and **BDD (Gherkin)** using `playwright-bdd`.

Business scenarios are written in plain English (`.feature` files), while all browser logic lives in reusable **Page Objects** and **Components**, injected into steps through **Playwright fixtures**.

## Tech stack

| Tool | Purpose |
|---|---|
| [Playwright Test](https://playwright.dev) | Test runner and browser automation |
| TypeScript | Type-safe test code |
| [playwright-bdd](https://github.com/vitalets/playwright-bdd) | Converts Gherkin `.feature` files into Playwright tests |
| Node.js 24 | Runtime |
| Git + GitHub | Version control |

### Why `playwright-bdd` instead of Cucumber-JS?

`playwright-bdd` **generates Playwright tests from the feature files**, so Playwright Test stays the runner. That keeps all of its built-in features: fixtures, parallel workers, retries, traces, projects (multi-browser), sharding and the HTML report. With Cucumber-JS as the runner, these would have to be rebuilt by hand.

## How the framework works

```
 .feature file        step definitions        fixtures           page objects / components      browser
 (WHAT to test)  -->  (glue, no locators) --> (DI: builds   -->  (HOW: locators + actions)  -->  (Playwright)
  plain English        *.steps.ts              page objects)      LoginPage, ProductsPage...
```

### Execution flow

1. `npx bddgen` reads `tests/bdd/features/*.feature` and the step files, and **generates** Playwright test files into `.features-gen/`.
2. `npx playwright test` runs those generated tests like any normal Playwright test.
3. For every test, Playwright creates a fresh browser page, and the **fixtures** build the page objects a step asks for.

### Layers

| Layer | Location | Responsibility |
|---|---|---|
| Features | `tests/bdd/features/` | Business scenarios in Gherkin. No code, no locators. |
| Step definitions | `tests/bdd/steps/` | Map each Gherkin sentence to page object calls and assertions. No locators. |
| Fixtures | `src/fixtures/fixtures.ts` | Create page objects per test and expose `Given / When / Then`. |
| Page objects | `src/pages/` | One class per page (URL). Own all locators and actions for that page. |
| Components | `src/components/` | Reusable UI blocks that appear on many pages (e.g. the left sidebar). |

```
│     ├─ features/              # .feature files, one per business area
│     │  ├─ auth.feature
│     │  └─ products.feature
│     └─ steps/                 # step definitions, organised by topic

├─ .gitattributes               # forces LF line endings for all OSs
├─ .gitignore
└─ package.json
```

### Key configuration (`playwright.config.ts`)

```ts
const testDir = defineBddConfig({
  features: 'tests/bdd/features/*.feature',
  steps: ['tests/bdd/steps/*.ts', 'src/fixtures/*.ts'],
});
```

- `testDir` points Playwright at the generated tests.
- The fixtures file is included in `steps` so playwright-bdd can load the custom `test`.
- `use.testIdAttribute: 'data-qa'` makes `page.getByTestId('login-button')` find `data-qa="login-button"` — the site's stable test attributes.

- Git

```bash
git clone https://github.com/prakashkr016/pw_ts_bdd.git
cd pw_ts_bdd
npm ci
npx playwright install
```

- `npm ci` installs the exact versions from `package-lock.json`.
- `npx playwright install` downloads the browsers.

### Test account

Some scenarios log in with a fixed, pre-registered account on automationexercise.com.

1. Register an account manually on the site.
2. Put its email and password in the `the user logs in with valid credentials` step (`tests/bdd/steps/auth.steps.ts`).
3. Put the same email in the "already registered email" scenario in `auth.feature`.

> Credentials are hardcoded for now. They will move to environment configuration in a later phase.

## Running tests

Always generate first, then run:

```bash
npx bddgen
npx playwright test
```

| Goal | Command |
|---|---|
| Run on Chromium only | `npx playwright test --project=chromium` |
| Watch the browser | `npx playwright test --project=chromium --headed` |
| Run by tag (e.g. smoke) | `npx playwright test --grep "@smoke"` |
| Run one feature area | `npx playwright test --grep "@auth"` |
| List tests without running | `npx playwright test --list` |
| Open the HTML report | `npx playwright show-report` |
| Debug step by step | `npx playwright test --debug` |

> On Windows PowerShell 5.1, run commands on separate lines — `&&` is not supported.

### Inspecting locators

```bash
npx playwright codegen https://www.automationexercise.com/products
```

Stop recording, open the **Locator** tab in the Inspector, and type a locator (without `page.` or `await`) to see what it highlights.

## Adding a new test

1. **Write the scenario** in the right `.feature` file (or create a new one per business area).
2. Run `npx bddgen`. It lists every **missing step** with a code snippet.
3. **Check for reuse.** Steps are global, so an existing step in any file can be used by any feature.
4. **Add locators and an action method** to the right page object or component.
   - New page → new class in `src/pages/`.
   - UI block on many pages → new class in `src/components/`.
5. **Register new page objects** as fixtures in `src/fixtures/fixtures.ts`.
6. **Write the step definition** in the matching `*.steps.ts`:
   - replace `({})` with the fixtures the step needs,
   - rename `arg`, `arg1` to meaningful names,
   - replace the comment with real code. **Never leave a generated snippet empty — an empty step passes.**
7. Run `npx bddgen` and `npx playwright test --project=chromium`.
8. Commit when green.

### Example

```gherkin
When the user logs in with email "user@example.com" and password "Secret@123"
```

```ts
// src/pages/LoginPage.ts
async login(email: string, password: string) {
  await this.loginEmailInput.fill(email);
  await this.loginPasswordInput.fill(password);
  await this.loginButton.click();
}

// tests/bdd/steps/auth.steps.ts
When('the user logs in with email {string} and password {string}',
  async ({ loginPage }, email: string, password: string) => {
    await loginPage.login(email, password);
  });
```

## Coding conventions

### Layer rules

1. **Feature files** contain only business language — no code, no locators.
2. **Steps** contain no locators; they call page object methods and make assertions.
3. **Page objects** own all locators for their page and contain no business assertions.
4. **One sentence = one step definition** across the whole project. Shared steps go in `common.steps.ts`.

### Page objects and components

- Fixed locators → `readonly` properties assigned in the constructor.
- Locators that depend on input → methods that return a `Locator`, named as nouns (`categoryLink(name)`).
- Action methods are named after **what the user achieves** (`login`, `searchFor`, `submitReview`), not browser actions (`fill`, `clickButton`).
- One page object per page/URL. UI shared across pages becomes a component.

### Locators

- Prefer, in order: `data-qa` via `getByTestId` → roles (`getByRole`) → ids / attributes → CSS classes.
- Scope locators inside a container when text repeats (`#Women` → "Dress").
- A **strict mode violation** means the locator is not unique — make it more specific instead of adding `.first()`.
- Use `.first()` only when any one of identical items is acceptable (e.g. the first product card).

### Assertions and data

- Use web-first assertions (`await expect(locator).toBeVisible()`) — they wait and retry.
- `allTextContents()` does not wait — wait for the first element before reading a list.
- Guard against empty lists (`expect(names.length).toBeGreaterThan(0)`) so loops cannot pass on nothing.
- New accounts use a unique email (`testuser.${Date.now()}@example.com`).
- Scenarios that create an account delete it at the end. The fixed test account is never deleted.

### Naming

| Item | Convention | Example |
|---|---|---|
| Feature file | lowercase, business area | `products.feature` |
| Steps file | `<area>.steps.ts` | `products.steps.ts` |
| Page object | PascalCase + `Page` | `ProductDetailsPage.ts` |
| Component | PascalCase | `LeftSidebar.ts` |
| Fixture | camelCase of class | `productDetailsPage` |

## Git workflow

After every green milestone:

```bash
git add .
git commit -m "short description of what changed"
git push
```

- `.features-gen/`, `test-results/`, `playwright-report/` and `node_modules/` are git-ignored.
- `.gitattributes` (`* text=auto eol=lf`) keeps line endings consistent between Windows and Linux CI.
